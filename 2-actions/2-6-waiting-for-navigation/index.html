A click waits for its navigation to start, not for the page to load

2.6 · Actions · click() · waitForURL() · waitForEvent()

What a click waits for after the mouse event, and what it does not.

A click can start a navigation of the page 1. Then the click waits until that navigation commits or fails. Commit means that the browser has switched to the new URL. The click does not wait for load. A navigation inside an iframe does not hold the click.

Source ↗

noWaitAfter: true skips this wait 2. The checks before the click still run. The log still prints waiting for scheduled navigations to finish, so that line alone does not prove that the click waited. The docs mark the option as deprecated: it will default to true in the future.

When the click returns, the new page may still be loading 3. waitForURL waits for the URL and, by default, for load. Data that the page fetches after load can still be missing. Check the content you need with an assertion.

waitForEvent starts listening when you call it 4. An event that came earlier is lost. Each event goes to your filter function first. The wait ends on the first event that passes, on the timeout, or when the page closes or crashes.

Source ↗

What you see in the call log

  • waiting for scheduled navigations to finishThe click reached its last stage. The line also prints with noWaitAfter, and after dblclick() and tap(), which never wait. It does not prove that a navigation started.
  • navigated to "…"The click started a navigation of the top frame, and the navigation committed. The new page can still be loading.
  • navigations have finishedThe click stops waiting. This does not mean the page is loaded or ready.
