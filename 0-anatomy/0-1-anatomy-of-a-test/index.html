API calls leave from Node, page calls from the browser

0.1 · Anatomy of a test · page · request

Web, API and combined tests pass through the same layers, but leave by different doors.

The output shown here is from Node.

The runner starts a worker process, and your test runs there 1. In the default local setup, the Playwright client and server both live in that worker. Each call becomes a message, but the message stays in the same process.

A web test asks for page 2. The fixtures start a browser, a context and a page. The browser is a separate process. Page actions go to it, and the page loads your app over the browser’s network.

An API test asks for request. This fixture needs only playwright, so no browser starts for it. Playwright sends the HTTP request from Node, with http or https.

Source ↗

page.request belongs to the page’s browser context 3. It sends that context’s cookies and stores response cookies there. So when the app keeps its login in a cookie, an API login also logs in the page. The request still leaves from Node, so page.route does not see it.

The request fixture has its own cookie jar 4. To reuse its login in a browser, take storageState() and give it to a new context. This copies the cookies once. After that, the two jars do not share changes.

What you see in the call log

  • navigating to "https://app.example/", waiting until "load"A page.goto() call. The browser loads the page.
  • → POST https://app.example/api/loginAn API request. Playwright sends it from Node, not from the page.
  • ← 200 OKThe API response status. The response headers follow, one per line.
  • set-cookie: session=…The response sets a cookie. It goes into the jar of the API context that sent the request.
