HAR candidates compete on matching headers

3.2 · Request, route and HAR · routeFromHAR()

Replay a recorded response, choose what happens when it is missing, or record a new HAR.

routeFromHAR() matches the request’s exact URL string and method 1. For POST, it compares bodies only when both requests have one. Multipart bodies can match despite different boundary strings. If several recorded requests match, the one with the most matching headers wins. Header names ignore case; values must match. A single match needs no header comparison.

Source ↗

The response follows redirects saved in the HAR 2. A recorded 301 or 302 changes POST to GET; 303 changes methods other than GET and HEAD. A navigation to another recorded URL changes the document URL. The response uses the recorded status, headers and body. Bodies can come from inline text, base64, external files or ZIP entries.

A request missing from the HAR aborts by default 3. Set notFound: 'fallback' to let the next matching handler answer. Lookup errors use the same choice and appear in API debug logs. The docs recommend serviceWorkers: 'block': requests answered by service workers are not served from HAR.

Set update: true to record requests instead of replaying the HAR 4. Recording defaults to minimal mode and attached bodies. Keep attached body files beside the HAR, or keep their ZIP entries. Call context.close() to export the recording.
